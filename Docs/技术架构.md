# 《城垒争锋》技术架构

## 程序集方向

`Core ← Runtime ← Presentation / Infrastructure ← Bootstrap`

- Core：纯 C# 标识、命令、快照和系统接口，不引用 Unity。
- Runtime：玩法系统和不可变 Match 配置，不直接加载资源。
- Presentation：ViewModel、UIPanel 和世界表现，不拥有玩法事实。
- Infrastructure：Addressables、存档、平台适配和资源租约。
- Bootstrap：唯一组合层，显式构造并注入系统。

禁止循环依赖、公共 Service Locator、平行单例和通过 Script Execution Order 修复初始化。

## 场景与生命周期

- Boot 创建持久组合根、加载配置/存档并进入 Selection。
- Selection 只处理局外状态和对局参数。
- Gameplay Installer 根据 BattlefieldId、MapModeId、MatchId 创建不可变 MatchConfigSnapshot 和场景系统。
- ResultPanel 在 Gameplay 内暂停，结算完成后返回 Selection。
- 系统初始化、订阅、暂停、场景卸载和 Shutdown 必须幂等且成对。

## 系统边界

- Economy/Building/Training/Research/Combat/Reward 等系统各自拥有状态和原子命令。
- UI 只发送命令并渲染 ViewModel；不能直接修改业务状态。
- AI 只生成业务命令；消费者再次校验资源、卡牌、槽位、路径和上限。
- 敌方后台设施没有 GameObject；Presentation 只显示采集者、携带物、工人、箭塔工地、箭塔和战斗实体。
- BuildingSystem 拥有运行/资源短缺暂停状态：消费失败时锁停，Economy 库存变化不驱动自动恢复；玩家 UI 或敌方 AI 只能通过正式 `Resume` 命令解锁，下一消费点仍会原子复核。

## Schema v14 资源系统

`MatchBattlefieldLayoutConfig` 冻结：

- 3+6+3 节点、墙体/路线、坐标、初始容量、刷新容量和刷新延迟。
- 初始波次随机：`MatchSeed + WaveId`。
- 节点刷新随机：`MatchSeed + NodeId + SpawnRevision`。

所有候选先按稳定 ID 排序。采集速度、Dictionary 顺序或其他节点耗尽时间不能改变后续初始波次。

采集命令必须携带预期 NodeId、ResourceId 和 SpawnRevision；版本不匹配时清除目标并重新查询，禁止隔空采集或命中刷新后的旧实例。

## Schema v14 奖励系统

`MatchHandAndOffersConfig` 冻结候选数量、五层稀有度权重、九个资源包、十个援军模板、冷却和三类奖励表现键。

- `RewardChoiceSnapshot` 携带 Kind、Rarity、Card/Resource/Template 数据。
- `GameplayRewardChoiceViewModel` 携带玩家可读名称、Details、Rarity 和 IconResourceKey。
- UI 不读取 Reward ScriptableObject。
- Offer 固定四项；资源直接入库；援军仅在合法部署事务成功后消耗。
- 箭塔卡属于建筑奖励候选但保持 BattlefieldItem 语义；玩家和敌方领取后都只能交给 TowerConstructionSystem，不能进入九格 BuildingSystem。
- 玩家奖励打开时使用独立 `PlayerRewardChoice` 暂停原因；敌方奖励不暂停玩家模拟。

## 确定性

- 固定 10 Hz Tick。
- 随机域独立：地图波次、节点刷新、奖励、AI、双方派遣不得共享可变随机状态。
- 使用稳定 ID 排序、版本化整数查找表和定点权重。
- 录像/复现至少保存 SchemaVersion、MatchSeed、地图、模式和关键命令序列。

### 城墙战斗几何

- `CombatSystem` 从冻结的三条路线首、末端点推导玩家/敌方纵向墙面；所有路线必须共享同一对边界，并满足 `PlayerGate < PlayerSurface < EnemySurface < EnemyGate`。Schema v14 当前两张地图的墙面均为 `X=518 / 1824`。
- 城墙覆盖战场纵向范围。单位攻击城墙时保持当前 Y，只计算水平距离；权威判定为“单位身体边缘到墙面的距离 `<= AttackRange`”，等价于单位中心到墙面的停止距离为 `AttackRange + CollisionRadius`。
- 单位中心必须限制在 `[PlayerSurface + CollisionRadius, EnemySurface - CollisionRadius]`；普通移动、友军分离和 Boss 击退共用这一钳制，表现层 Collider 不参与玩法判定。
- 单位单次移动后若刚好进入墙体射程，同一 Tick 立即锁定并攻击。墙体弹体命中点为对应墙面 X 与发射者当时的 Y，不再使用城门中心点。

## UI 和表现

- `UIManager` 只管理 UIPanel 生命周期和 Bg/Window/Pop/Over 层。
- Panel 根节点全屏拉伸；Prefab 保存子布局；交互位于 Safe Area。
- 世界表现读取 Snapshot，使用资源租约生成/回收；不得把 Transform 当权威坐标。
- 对象池为 internal；租约释放必须处理取消、场景卸载和二次回收。

## Addressables

- 只有 Infrastructure 调用 Addressables。
- 业务使用稳定 ResourceKey/SceneKey。
- Gameplay Installer 必须预加载该场景需要的 Sprite/GameObject 键，类型不能混用。
- Local-Core、Local-UI、Local-Gameplay、Local-Audio、Local-Scenes 为当前本地组。

## 存档

- Save DTO 只保存永久金币、解锁、等级、设置和必要的幂等结算信息。
- 不保存 Unity Object、AssetReference、Handle 或场景实例。
- MatchId 用于防重复结算；Schema v14 没有修改已发布稳定 ID 或存档 DTO。

## 故障与验证

- 当前 Unity Editor Build Target 为 Android；平台切换后必须重新建立该目标下的编译、Console、测试和 Addressables 证据。
- 配置加载、缺失引用、类型错误和重复 ID 立即失败，不做静默兜底。
- 每次脚本修改：编译 → Console → 定向测试。
- 高风险资产：MCP/Editor API 修改 → 回读 → 内容校验 → PlayMode。
- 完整 Editor 门槛：Android 目标下的非 Explicit EditMode、PlayMode、Prefab/Importer/Addressables 回读、双分辨率截图和 Android Local Content Build。
- Android 交付门槛另含 ARM64 IL2CPP Player 构建、安装启动、真机完整流程、Safe Area、触控、生命周期和性能验证；不得由 Editor 结果代替。
- 1800 局矩阵只能分为 36×50 子批，避免阻塞 Unity 主线程。
